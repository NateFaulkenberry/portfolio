# Nate Faulkenberry's Portfolio

A personal portfolio site built with **Next.js** (App Router, TypeScript) and **Tailwind CSS**, exported as a **fully static site**, and deployed to **GitHub Pages** by GitHub Actions.

All portfolio content lives in Markdown files under [`content/`](content/). To update the resume, add a project, or list an album, you edit a Markdown file and push. You never need to touch React code.

```text
Markdown / content files  →  Next.js build  →  static export (out/)  →  GitHub Pages artifact  →  public website
```

There is no server, database, API, or CMS. The Git repository *is* the CMS.

## Local development

Everything runs in Docker. You don't need Node.js or npm installed.

```bash
docker compose up
```

Then open **http://localhost:3000**.

The source tree is mounted into the container, so edits to components, styles, and content show up without restarting. Markdown content is re-read on every request, so refresh the page after saving a `.md` file.

| Task | Command |
| --- | --- |
| Start dev server | `docker compose up` |
| Start on another port | `DEV_PORT=3001 docker compose up` |
| Stop | `Ctrl+C`, or `docker compose down` |
| After changing `package.json` | `docker compose up --build --renew-anon-volumes` |

<details>
<summary>Without Docker (optional)</summary>

With Node.js 24 (see `.nvmrc`):

```bash
npm ci
npm run dev
```

</details>

## Production build

Generate the static site into `./out`:

```bash
docker compose run --rm build
```

This runs the same checks as CI: typecheck → lint → static export → export verification. The command fails if any step fails.

Preview the exported files the way GitHub Pages will serve them (nginx, no Node):

```bash
docker compose up preview          # http://localhost:8080
```

### Testing the GitHub Pages sub-path

Project sites are served from `https://<user>.github.io/<repo>/`. To build and preview exactly that:

```bash
BASE_PATH=/portfolio docker compose run --rm build
BASE_PATH=/portfolio docker compose up preview    # http://localhost:8080/portfolio/
```

A rebuild replaces `./out`, so if the preview is already running, restart it with `docker compose restart preview`. Use `PREVIEW_PORT=8081` if port 8080 is taken.

A standalone image containing the built site is also available:

```bash
docker build --target site -t portfolio-site .
docker run --rm -p 8080:80 portfolio-site
```

## Content management

| File / folder | Page | What it holds |
| --- | --- | --- |
| `content/home.md` | `/` | Introduction paragraph on the home page |
| `content/resume.md` | `/resume` | The resume, as a Markdown document |
| `content/cv.md` | `/cv` | The CV, as a Markdown document |
| `content/code/*.md` | `/code` | One file per software project |
| `content/design/*.md` | `/design` | One file per design project |
| `content/audio/*.md` | `/audio` | One file per album / audio project |
| `content/<section>/_index.md` | section header | Title and introduction for Code, Design, Audio |

The typical workflow:

```bash
vim content/resume.md
git add .
git commit -m "Update resume"
git push
```

GitHub Actions rebuilds and redeploys the site automatically.

### Resume and CV

These are ordinary Markdown files. Headings, paragraphs, **bold**, *italic*, lists, links, blockquotes, code, horizontal rules, and tables are all supported and styled as a professional document. Suggested conventions:

```markdown
## Experience            ← section heading (rendered as a ruled section label)

### Company Name         ← entry heading

**Role** · 2022 – 2026   ← first line under an entry renders as a muted subtitle

- Achievement
```

Optional frontmatter:

```yaml
---
title: Resume
updated: 2026-09-01         # shown as "Updated September 2026"
pdf: /downloads/resume.pdf  # generated by the build; adds a "Download PDF" link
---
```

The resume and CV pages also print cleanly: site chrome is hidden and the text is set in black. `npm run build` uses that print layout to generate each page's `pdf` file: after the static export, `scripts/build-pdfs.mjs` prints `/resume/` and `/cv/` with headless Chrome and writes the PDFs to `public/downloads/` (commit them) and to `out/`. It needs Chrome or Chromium installed; set `CHROME_PATH` if it is somewhere unusual. `npm run pdf` regenerates them from an existing build.

### Portfolio entries

Each entry is a Markdown file with YAML frontmatter. The frontmatter holds the structured fields. The Markdown body below it is the optional longer write-up. The filename becomes the entry's anchor (`/code/#my-project`).

Fields shared by all collections:

| Field | Required | Notes |
| --- | --- | --- |
| `title` | yes | |
| `description` | yes | One or two sentences, used on cards |
| `image` | | Path under `public/`. A placeholder shows until the file exists |
| `year` | | `2026` or `"2024–2026"` |
| `tags` | | `[TypeScript, Audio DSP]` |
| `featured` | | `true` to show the entry under *Selected work* on the home page |
| `order` | | Number. Lower numbers sort first. Otherwise featured entries come first, then newest `year`, then title |
| `links` | | Extra links, as a list of `label` + `url` entries |

Each example file in `content/code/`, `content/design/`, and `content/audio/` has a comment block listing every field for that collection.

If a required field is missing or a URL is malformed, **the build fails** with a message naming the file and field, so a typo never ships silently.

To remove the example entries, delete the `example-*.md` files.

## Assets

Static files live in `public/` and are served from the site root:

```text
public/
├── images/
│   ├── profile/    # profile photo (nate.jpg by default; see lib/site.ts)
│   ├── code/       # code project screenshots
│   ├── design/     # design screenshots (16:10 crops best)
│   └── audio/      # album artwork (square)
├── downloads/      # resume.pdf, cv.pdf (generated by the build), other downloads
└── assets/         # anything else
```

Refer to files with root-relative paths such as `/images/code/my-project.jpg`, both in frontmatter and in Markdown bodies. The build adds the GitHub Pages base path automatically.

Images that don't exist yet are fine. Each page shows a designed placeholder until you add the file.

**Profile photo:** add `public/images/profile/nate.jpg`, ideally a portrait crop around 4:5. To use a different filename, change `photo` in `lib/site.ts`. The frame crops from the top by default. Adjust `photoPosition` (e.g. `"center 15%"`) to shift which part of the photo stays visible.

## Adding a code project

1. Create `content/code/my-project.md`:

   ```markdown
   ---
   title: My Project
   description: A one-sentence summary of what it does.
   image: /images/code/my-project.jpg
   github: https://github.com/NateFaulkenberry/my-project
   url: https://my-project.example.com
   tags: [TypeScript, WebAudio]
   year: 2026
   featured: true
   ---

   The longer write-up: the problem, the approach, and the result.
   ```

2. Add `public/images/code/my-project.jpg` (optional).
3. Commit and push.

## Adding design work

1. Create `content/design/my-site.md`:

   ```markdown
   ---
   title: My Site
   description: Short description of the project and your role.
   image: /images/design/my-site.jpg
   url: https://my-site.example.com
   category: Website
   tags: [Branding, Next.js]
   ---

   Optional notes on the design goals and process.
   ```

2. Add `public/images/design/my-site.jpg` (optional).
3. Commit and push.

## Adding audio

1. Create `content/audio/my-album.md`:

   ```markdown
   ---
   title: My Album
   artist: Artist Name
   role: Recording / Mixing
   description: Short description of the record and your contribution.
   image: /images/audio/my-album.jpg
   url: https://open.spotify.com/album/...
   year: 2026
   links:
     - label: Bandcamp
       url: https://artist.bandcamp.com/album/my-album
   ---
   ```

2. Add `public/images/audio/my-album.jpg` (optional; square artwork).
3. Commit and push.

## Site configuration

Name, title, tagline, location, email, phone, the profile photo path, and social links are all defined once in [`lib/site.ts`](lib/site.ts):

```ts
export const siteConfig = {
  name: "Nate Faulkenberry",
  title: "Nate Faulkenberry's Portfolio",
  location: "Glastonbury, CT",
  email: "nate.faulkenberry@gmail.com",
  phone: "(860) 710-0897",
  photo: "/images/profile/nate.jpg",
  social: {
    github: "https://github.com/NateFaulkenberry",
    linkedin: "", // ← add your LinkedIn URL here
  },
};
```

Until `linkedin` is set, LinkedIn appears as muted, non-linked text.

## Deployment

```text
git push (main)
    ↓
GitHub Actions  (.github/workflows/deploy.yml)
    ↓
npm ci → typecheck → lint → next build → verify
    ↓
static export (out/)
    ↓
actions/upload-pages-artifact → actions/deploy-pages
    ↓
GitHub Pages
```

The workflow runs on every push to `main` and can also be started manually from the **Actions** tab (**Deploy to GitHub Pages** → **Run workflow**).

### One-time GitHub setup

1. Push this repository to GitHub.
2. Go to **Settings → Pages → Build and deployment → Source** and select **GitHub Actions**.
3. Push to `main`, or run the workflow manually. The deployment URL appears in the workflow summary and under **Settings → Pages**.

### Base path

GitHub Pages serves:

- **user sites** (a repo named `<user>.github.io`) and custom domains from `/`
- **project sites** (any other repo name) from `/<repo>/`

The workflow reads the correct values from `actions/configure-pages` and passes them to the build as `BASE_PATH` and `SITE_URL`. `next.config.ts` applies the base path to every route, script, stylesheet, and font. The helper `assetUrl()` in `lib/site.ts` applies it to images and downloads, including links written inside Markdown. Nothing is hard-coded to `/`, so renaming the repository or adding a custom domain requires no code changes.

```text
scripts/verify-export.mjs  Post-build check of the static output
docker/                 nginx config for local static previews
Dockerfile, docker-compose.yml

```

## Validation

`npm run check` (run inside Docker by `docker compose run --rm build`, and by CI) performs:

| Step | What it catches |
| --- | --- |
| `typecheck` | TypeScript errors |
| `lint` | ESLint (Next.js core-web-vitals and TypeScript rules) |
| `build` | Static export and resume/CV PDFs; content errors such as missing required fields or bad URLs |
| `verify` | Every route exported, every Markdown page rendered, every content entry present on its page, and every internal link, image, script, stylesheet, and font URL resolving to a real file under the configured base path |
